## Propósito
Integrar la seguridad en todo el ciclo de vida del software (enfoque *Shift Left*), desde el diseño hasta el despliegue y el mantenimiento, para que la seguridad sea parte de la arquitectura, el código y la operación.

## Alcance
Aplica a todo desarrollo interno y a las contribuciones de terceros: aplicaciones web y móviles, APIs, integraciones, infraestructura como código, *pipelines* de CI/CD y componentes que usen modelos de inteligencia artificial.

## Ciclo de Vida de Desarrollo Seguro (SDLC)
| Fase | Actividades de seguridad mínimas |
| ---- | -------------------------------- |
| Planificación y diseño | Requisitos de seguridad basados en riesgo; modelado de amenazas para funcionalidades nuevas o críticas. |
| Desarrollo | Estándares de codificación segura; análisis estático (SAST); detección de secretos; análisis de dependencias (SCA). |
| Revisión | Revisión de código por pares en todo *pull request*, con lista de verificación de seguridad para los cambios sensibles. |
| Pruebas | Pruebas dinámicas (DAST) en entornos de prueba; pruebas de penetración antes de lanzar sistemas críticos o cambios mayores. |
| Despliegue | *Pipeline* automatizado con controles que bloquean vulnerabilidades críticas; despliegues aprobados conforme a la Política de Gestión de Cambios y Configuraciones. |
| Operación | Monitoreo, gestión de vulnerabilidades y respuesta a incidentes. |

## Estándares de Codificación Segura
- Aplicar como referencia el OWASP Top 10 y, para aplicaciones críticas, OWASP ASVS nivel 2.
- Validar y sanear todas las entradas; codificar las salidas; usar consultas parametrizadas.
- Aplicar mínimo privilegio, manejo seguro de errores (sin exponer información interna) y registro de eventos de seguridad.
- **Nunca** almacenar secretos en el código ni en los repositorios: usar un gestor de secretos.

## Seguridad en APIs
- Mantener un inventario actualizado de las APIs (internas, externas y de terceros), con propietario y clasificación de datos.
- Autenticación robusta (OAuth 2.0/OIDC o tokens firmados) y autorización por objeto y función (OWASP API Security Top 10).
- Limitación de solicitudes (*rate limiting*), validación de esquemas y respuestas que no expongan datos innecesarios.
- APIs publicadas a través de un *gateway* o WAF, con registro y monitoreo.

## Separación de Entornos y Datos de Prueba
- Los entornos de desarrollo, prueba y producción están separados, sin confianza automática entre ellos.
- Los entornos de prueba que contienen datos reales tienen controles de acceso equivalentes a producción.
- Los datos de producción solo se usan en pruebas si están anonimizados o enmascarados; su uso se registra y se eliminan al terminar.

## Componentes de Terceros y Cadena de Suministro de Software
- Usar librerías y servicios de fuentes confiables, con licencia compatible y mantenimiento activo.
- Generar un inventario de componentes (SBOM) para las aplicaciones críticas.
- Actualizar los componentes con vulnerabilidades según los plazos de la Política de Gestión de Vulnerabilidades y Parches.
- Proteger el *pipeline*: ramas principales protegidas, revisiones obligatorias, firmas o verificación de artefactos y permisos mínimos para los *runners*.

## Firewall de Aplicaciones Web (WAF)
Las aplicaciones web expuestas a internet se protegen con un WAF configurado contra ataques conocidos y ajustado a la funcionalidad de cada aplicación.

## Uso de Asistentes de IA en el Desarrollo
El código generado o sugerido por herramientas de IA se revisa con el mismo rigor que el código humano y solo se usan herramientas aprobadas conforme a la [Política de Uso Aceptable de Inteligencia Artificial](/sgx/politicas-y-procedimientos/politica-de-uso-aceptable-de-inteligencia-artificial).

## Cumplimiento
El cumplimiento de esta política es obligatorio para todos los equipos de desarrollo y proveedores. El incumplimiento puede generar acciones disciplinarias o contractuales.

## Monitoreo y Revisión
- Indicadores mínimos: vulnerabilidades abiertas por severidad, tiempo de remediación y porcentaje de repositorios con SAST/SCA activos.
- Revisión anual de esta política bajo la supervisión del Responsable de Ciberseguridad y del Líder de Desarrollo.
