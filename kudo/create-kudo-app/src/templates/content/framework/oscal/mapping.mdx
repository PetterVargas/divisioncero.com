El modelo **Mapping** (OSCAL 1.2) expresa *cómo se relacionan los controles de dos catálogos*. Kudo lo usa para publicar en formato máquina las páginas de [Correlación](/sgx/correlacion) del SGX: cada control de un estándar se relaciona con los controles Kudo que lo atienden.

| Elemento | Uso en Kudo |
| -------- | ----------- |
| `provenance` | Método `hybrid`, criterio `semantic`, estado `complete` |
| `source-resource` | Referencia al estándar (su texto no se redistribuye) |
| `target-resource` | [Catálogo Kudo](/framework/oscal/catalog) |
| `maps` | Un `map` por control del estándar con relación `intersects-with`; `sources` es el control del estándar y `targets` los controles Kudo |
| `props` / `links` | Código y enlace del documento del SGX que sustenta la relación |

## Cómo se construye

La relación se deriva en dos pasos, ambos versionados en el repositorio:

1. **Estándar → documento SGX:** la tabla de cada página "Controles … con SGSI" de la correlación.
2. **Documento SGX → controles Kudo:** el campo `controles` del frontmatter de cada política.

Por eso la relación se declara como `intersects-with` (el control del estándar y los controles Kudo comparten objetivo, no son equivalentes uno a uno). Al actualizar una política o una tabla de correlación, regenera el modelo:

```bash
pnpm kudo:oscal       # json, yaml y toon
pnpm kudo:oscal:xml   # valida y genera el XML
```

<Callout title="Brechas como hoja de ruta">
  Los controles en `target-gap-summary` indican dónde la correlación del estándar todavía no apunta a la política del SGX que cubre ese control. Son un buen punto de partida para revisar las tablas de correlación.
</Callout>
